# Service Object Storage

This service will provide a common interface to storage for artifacts produced
by retailer sourcing. It will start with a separate PostgreSQL database as its
storage backend.

The service will use axum as an intentional exception to the poem convention
for new services, to evaluate whether axum is easier to work with than poem.
See [ADR 5](adr/0005-axum-for-object-storage.md).

The service will expose two types of access: a REST-style HTTP API and a
GraphQL API.

The long-term storage backend remains undecided. PostgreSQL may remain the
backend, or the service may move to an object storage system such as MinIO.

## Records

The PostgreSQL `records` table will have these columns:

| Column            | PostgreSQL type | Purpose                                                   |
| ----------------- | --------------- | --------------------------------------------------------- |
| `id`              | `uuid`          | Primary key, always a UUIDv7 generated by the service.     |
| `bucket`          | `text`          | Bucket name from a hard-coded allowlist.                   |
| `external_id`     | `uuid`          | Client-supplied UUIDv7 identifying a creation request.     |
| `data_id`         | `uuid`          | Required foreign key referencing `data.id`.                |
| `metadata`        | `jsonb`         | Artifact metadata.                                        |
| `created_at`      | `timestamptz`   | Service-generated creation timestamp, represented in UTC. |

Artifact content is stored separately in the PostgreSQL `data` table:

| Column    | PostgreSQL type | Purpose                                               |
| --------- | --------------- | ----------------------------------------------------- |
| `id`      | `uuid`          | Primary key, a separate UUIDv7 generated by the service. |
| `payload` | `text`          | Artifact content.                                     |

All columns in both tables are required. Clients supply the bucket,
idempotency key, payload, and metadata. The service generates both IDs and
`created_at`, and sets `records.data_id`; clients cannot set these fields.
Each new record is created together with a new data row in one transaction,
even when another data row already contains the same payload. `data_id` is
not unique: multiple records may reference the same data row after
deduplication.

Records are immutable through the APIs, which expose creation and retrieval
only, with no update or delete operations. Retrieval resolves `data_id` to
return the payload alongside the record's other fields. The data ID is an
internal storage detail and is not exposed by either API.

### Idempotency

The pair `(bucket, external_id)` uniquely identifies a record. The same
idempotency key may be used independently in different buckets. Enforce this
with a unique constraint on `(bucket, external_id)`.
The database column `external_id` is supplied as `idempotency_key` in REST
and `idempotencyKey` in GraphQL.

Both record IDs and idempotency keys must be valid UUIDv7 values. Clients
generate the idempotency key and reuse it for retries; the service generates
the record ID. Both APIs accept and return UUIDs as strings. Compare
idempotency keys by their parsed UUID value.

When a creation request uses an existing pair:

- If both payload and metadata match, return only the existing record's ID.
- If either differs, return `409 Conflict` in REST or a `CONFLICT` execution
  error in GraphQL.

Compare payloads exactly after decoding the request's JSON string. Compare
metadata as JSON values, independent of object-key order. A retry must neither
modify the existing record nor persist a new record or data row. These rules
also apply to concurrent requests: only one record may be committed for a
given pair, and competing requests must resolve against its content.

### Deduplication

A separate process is planned to deduplicate stored payloads after creation,
allowing multiple records to reference one data row. Each record's API-visible
content must remain unchanged.

Deduplication is deferred to a later design discussion and implementation.
Its scope, payload-matching rules, scheduling, batching, cleanup, and
concurrency behavior, including retrieval during deduplication, remain open.

### Storage and retrieval rules

The service imposes no size limits on payloads, metadata, or HTTP request
bodies in either API. Framework and middleware defaults that limit
request-body size must be disabled. PostgreSQL's inherent storage
restrictions still apply.

Retrieval requires both `bucket` and `id`. A record is returned only when both
match. Creation returns only the new or existing record's ID; retrieval
returns the record.
Timestamps in API responses use RFC 3339 with the UTC `Z` suffix.

Bucket names are case-sensitive strings from a hard-coded allowlist. Arbitrary
bucket names and dynamic bucket creation are not supported. Confirmed names:

- `sitemap_raw` (legacy name, retained)
- `sitemaps_raw` (raw sitemap bodies from retailer sourcing)
- `sitemap_processed` (legacy name, retained)
- `sitemaps_processed`
- `sitemap_consolidated` (legacy name, retained)
- `sitemaps_consolidated`
- `offer_details_raw`
- `offer_details_extracted`
- `offer_details_normalized`
- `offer_details_structuralized`

Integration with `retailer_sourcing` is out of scope for the current design

## REST-style API

| Method | Path                                 | Behavior                                 |
| ------ | ------------------------------------ | ---------------------------------------- |
| `POST` | `/api/buckets/{bucket}/records`      | Create a record in the specified bucket. |
| `GET`  | `/api/buckets/{bucket}/records/{id}` | Retrieve a record by bucket and ID.      |

Creation accepts `application/json` with required `idempotency_key` (a UUIDv7
string), `payload` (a string), and `metadata` (a JSON value) fields. Unexpected
request fields are rejected.
A successful creation returns `201 Created`, a `Location` header pointing to
the retrieval URL, and a JSON body containing only `id`:

```json
{"id": "019a1234-5678-7000-8000-000000000001"}
```

A matching idempotent retry returns `200 OK`, the existing record's retrieval
URL in `Location`, and the same JSON body shape containing only its `id`.

Successful retrieval returns `200 OK` with `id`, `bucket`, `idempotency_key`,
`payload`, `metadata`, and `created_at` in an `application/json` response.

## GraphQL API

GraphQL is served at `/graphql` using HTTP `POST` with an `application/json`
request body containing `query`, optional `variables`, and optional
`operationName`. Responses use `application/graphql-response+json`. Both
operations use the same validation and storage behavior as the REST-style API.

```graphql
scalar JSON
scalar DateTime

type StoredRecord {
  id: ID!
  bucket: String!
  idempotencyKey: String!
  payload: String!
  metadata: JSON!
  createdAt: DateTime!
}

input CreateRecordInput {
  bucket: String!
  idempotencyKey: String!
  payload: String!
  metadata: JSON!
}

type CreateRecordPayload {
  id: ID!
}

type Query {
  record(bucket: String!, id: ID!): StoredRecord
}

type Mutation {
  createRecord(input: CreateRecordInput!): CreateRecordPayload!
}
```

Bucket strings must belong to the allowlist. Record IDs and idempotency keys
must be valid UUIDv7 strings. The creation payload exposes only `id` within
the standard GraphQL `data` envelope. Retrieval allows callers to select the
record fields they need. A missing record returns `null` for `record` and a
`NOT_FOUND` error.
`DateTime` serializes as RFC 3339 in UTC. Metadata must be non-null in both APIs.

## Access

Both APIs initially require the same hard-coded bearer token, configured in
service code. Clients send `Authorization: Bearer <token>` on every request.
There is no per-bucket authorization initially. Missing or invalid credentials
are rejected before executing an operation with `401 Unauthorized` and a
`WWW-Authenticate: Bearer` challenge. The actual token value is not specified
in this document.

## Errors

REST errors use [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html) with content type
`application/problem+json` and the fields `type`, `title`, `status`, and
`detail`. Use `about:blank` as the problem type and the HTTP status phrase as
the title. Details describe the failure without exposing database errors or
the bearer token.

| Condition                                          | HTTP status                  | GraphQL `extensions.code`                          |
| -------------------------------------------------- | ---------------------------- | -------------------------------------------------- |
| Malformed input, unknown bucket, or invalid UUIDv7 | `400 Bad Request`            | `BAD_USER_INPUT`                                   |
| Missing or invalid bearer token                    | `401 Unauthorized`           | Not applicable: rejected before GraphQL execution. |
| No record matching both bucket and ID              | `404 Not Found`              | `NOT_FOUND`                                        |
| Existing bucket and idempotency key with different content | `409 Conflict`       | `CONFLICT`                                         |
| Unsupported request content type                   | `415 Unsupported Media Type` | Not applicable: rejected before GraphQL execution. |
| Unexpected server failure                          | `500 Internal Server Error`  | `INTERNAL_SERVER_ERROR`                            |
| Storage temporarily unavailable                    | `503 Service Unavailable`    | `SERVICE_UNAVAILABLE`                              |

GraphQL execution errors use the [standard `errors` array](https://spec.graphql.org/September2025/#sec-Errors) with `message`,
`path` and `locations` where applicable, and an `extensions.code` from the
application-defined codes above. Execution results use HTTP `200` and may
contain partial `data`. The HTTP statuses in the table apply to REST errors
and failures rejected before GraphQL processing; they do not replace HTTP
`200` for GraphQL execution errors.

GraphQL request errors prevent execution and return HTTP `400` with content
type `application/graphql-response+json`. The response contains an `errors`
array and omits `data`. Each error includes a descriptive `message`,
`locations` where applicable, and one of these `extensions.code` values:

| Condition | GraphQL `extensions.code` |
| --------- | ------------------------ |
| GraphQL document has invalid syntax | `GRAPHQL_PARSE_FAILED` |
| GraphQL document fails schema validation, such as an unknown field or missing required argument | `GRAPHQL_VALIDATION_FAILED` |
| Variable values cannot be coerced to their declared types, including a missing required variable | `BAD_USER_INPUT` |
| Operation cannot be selected, such as an unknown `operationName` or multiple operations without `operationName` | `OPERATION_RESOLUTION_FAILURE` |

Failures rejected before GraphQL processing, such as malformed JSON, missing
credentials, or an unsupported content type, use the HTTP status and Problem
Details format above.

## Open decisions

- Define retention and any administrative cleanup outside the immutable APIs.
- Discuss deduplication separately, including its scope, matching rules,
  scheduling, batching, cleanup, and concurrency behavior.

> [!WARNING]
> The initial PostgreSQL backend and JSON APIs cannot store all possible data:
>
> - NUL characters (U+0000) cannot be stored in the text fields or in metadata
>   strings and object keys. Sending a JSON `\u0000` escape does not bypass
>   this restriction: it represents the same character after decoding.
> - Raw binary data and text in non-UTF-8 encodings cannot be sent as payloads
>   directly. Clients must first encode binary data as text, such as Base64,
>   or decode source text and send it as a valid UTF-8 JSON string.
> - Metadata numbers outside PostgreSQL's `numeric` range cannot be stored in
>   `jsonb`, even if their JSON representation is syntactically valid.
>
> The database must use UTF-8 encoding to support the API's Unicode strings;
> another database encoding can reject additional characters. See PostgreSQL's
> [character type restrictions](https://www.postgresql.org/docs/current/datatype-character.html)
> and [JSON type restrictions](https://www.postgresql.org/docs/current/datatype-json.html).
